## 2. 对标技术优势分析（可迁移性 + 代价）

### 2.1 NNUE 强引擎（Pikafish / 皮卡鱼）在本项目有没有位置？

**结论：没有位置，且不应重启该议题。** 三条独立理由，任意一条都足以否决：

1. **规则不兼容（决定性）**：Pikafish 源自 Stockfish，面向**标准 9×10 中国象棋**；本项目主档是 **13×13 自定义兵种变体**（完整档 11 类 50 子、含尉/射/檑/巡与星轨、复活、升变；`docs/ARCHITECTURE.md:11-16`）。通用引擎的走法生成与 NNUE 输入特征（棋子-位置平面）都不认识这些兵种与规则，NNUE 权重迁移到 13×13 需要重新定义特征空间并重训——这不是"接一个引擎"，是"造一个新引擎 + 新训练集"。
2. **硬约束冲突**：NNUE 权重是独立大文件，Pikafish 自 2026-01 起输入特征加**威胁编码**、引擎与权重**必须成对替换**；权重分发/更新天然倾向在线获取，与"零联网依赖、纯本地"冲突。项目离线 PWA 靠 `webapp/js/core/rules.js` 自带规则镜像运行，无任何可挂载二进制引擎的位置。
3. **用户已裁定**：外部强引擎接入（对战与云分析）明确不做。

**可迁移的只有方法论，不是引擎**：Pikafish 移除 `UCI_LimitStrength/UCI_Elo` 后改用**限制搜索节点数或深度**来做强度阶梯，这个思路在 §2.3 讨论。但"限深降棋力"在本项目已由 `CONFIGS` 的 `depth`/`root`/`branch` 参数实现（`core/ai.py:139-158`），不需要外部引擎。

**代价若强行迁移**：新增 UCI/UCCI 进程间协议层 + 引擎二进制多平台打包（vnni512/avx512/bmi2/avx2/sse41 指令集分流）+ NNUE 权重随包分发 + 变体规则适配层 + 重训数据；以 1–3 人团队计，成本量级为**季度级**，且收益（棋力）不是本项目目标（项目定位是本地对战/教学/题库，不是竞技引擎）。

### 2.3 Pikafish「限深降棋力」对 K3-a 未达标有无**非调参**缓解价值？

先把 K3-a 定性钉死，避免误判：

- `docs/AI_TIERS.md:186`：K3-a v2 定义 `avoidable_hangs`（同一棋子只首次被攻击计数 + 走前 eval ±300cp 内 + SEE 门槛），硬线**最长连送 ≤2 手**；实测 root16 A 4/B 3、root18 A 3/B 3——**计数达标、连送条款未达标**。
- `:198`：**"连送未达标是结构性的，与 root 选择无关"**（两轮同向，属单事件量级）。
- 用户裁定：按预登记**本轮不调参**，列入 S5 观察项；K4 读取 `contractPass=false` 不可认证，不写成"已验证失败"。

**Pikafish 方法论的真实价值（有，但边界明确）**：

Pikafish 的做法是**把"棋力弱化"从伪装的 Elo 数字，改为可控、可公开、可复现的资源上限**（节点数/深度/movetime）。映射到本项目：

- 正面印证：`core/ai.py:140-147` 的 B1 陪练档**已经**是这个思路——弱化靠"从第 2..N 名按概率取样"（`randomness=0.18`、`sample_margin=150`），明确注释"不靠降深度/降时间"，并把三个旋钮（触发概率/水平下限/候选数）分开定义、禁止混调。也就是说，项目**已经采用了 Pikafish 式"单一可控旋钮"原则**，只是旋钮是取样概率而非深度。
- **非调参的描述框架**：可以把 K3-a 未达标重新描述为"当前弱化旋钮的一个**已知副作用**"——概率取样偶尔会选中可避免送子的次优着，形成连送。这个描述**不改变任何参数、不改变任何代码**，只改变结论的归因精度：K4 出带是 d1→d2 的战术质变（`AI_TIERS.md:330`），K3-a 连送是取样旋钮的尾部行为，两者是**不同机制、不可互相代替**。这有真实价值：它阻止了"再调一次参数碰碰运气"的冲动，也让 S5 观察项有了明确的观察对象。
- **不能做的事**：不能把"限深"当作修复 K3-a 的手段。降深度会削弱战术视野，理论上**加剧**送子而非减少；且任何 `depth`/`randomness`/`sample_margin` 改动都是调参，被裁定禁止。**因此本轮不产生任何行动项。**

一句话：**有解释价值，无修复价值；它证明"不调参"是正确的裁定，而不是绕开裁定的后门。**

## 5. 技术面上最大的结构性风险（一句话）

**三端共享核心的"单一真相"其实是靠产物链 digest 与跨引擎对拍****间接维持**的——`webapp/js/core/rules.js`（703 行手写 JS 镜像）与 Python `core/rules.py` 是**两套独立实现**，对拍能抓"不一致"却抓不到"一致地错"（同源 bug 两侧同时复现），而 `sourceDigest` 把 bundle 字节纳入哈希又意味着任何一次规则/文案改动都必须穿透 S1–S6 全链与两份 24.8 MB fixtures 才能保持门禁绿——**这套"脆弱-but-严格"的耦合既是当前质量的来源，也是未来任何规则演进都必须先付的重量级过路费**；K3-a 连送之所以"结构性、不可调参修复"，正是这一内核难以被安全地局部替换的直接体现。

> 补充判据：C-1 的"三端同源后一致地错"问题，主理人是用人工逐键交叉核验兜住的（`.workbuddy/memory/2026-11-23.md:113-115`："这是防「三端同源后一致地错」的唯一手段 —— 对拍抓不到"）。这句话是上述风险的直接证据：**唯一**手段 = 没有自动手段。

## 6. 与调度方判断不一致（前提有误，逐条更正）

> 按纪律：发现前提有误必须写明。以下均已实测复核，不修改原前提来源文件。

1. **reduced-motion 的 API 存在性**：调度方前提写"桌面 reduced-motion 无系统级入口（Qt 6.12 其实有 `accessibility().motionPreference()`，缺 Windows 真机 A/B）"——**方向正确**。`KNOWN_ISSUES.md:84-91` 的记载（"QStyleHints 实测未暴露 reduced-motion / 关闭动效属性，仅 colorScheme、useHoverEffects 等"）**不完整**：本机 `PySide6 6.12.0` 实测 `QGuiApplication.accessibility()` 不存在，但 `app.styleHints().accessibility()` 返回 `QAccessibilityHints`，其公开成员含 `motionPreference` / `motionPreferenceChanged` / `contrastPreference`；`motionPreference()` 返回 `MotionPreference.NoPreference`，枚举成员为 `NoPreference`、`ReducedMotion`。**准确表述**：API 在 6.12 可用，但缺的是 Windows 真机 A/B（offscreen 下恒为 `NoPreference`），且 `KNOWN_ISSUES.md` 的"未暴露"结论需更新。这是 T3 的立项依据。
