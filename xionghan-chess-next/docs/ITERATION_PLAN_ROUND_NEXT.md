## 0. 执行摘要（制作人裁决）

**一句话结论**：本轮胜负手不是"加新玩法"，而是**把已花大力气做好的复杂规则变得可理解、可分层、可试走**，并把已有能力（局势评估、终局判定）产品化；同时在视觉侧做**收敛与门禁补齐**，而非堆新项。

- **三方最高共识项**：「局势评分 + 逐步点评」——游有方列 P0、柯桥良技术实算 4.15 分首推，且底层 `core/analysis.py`（`analyze_game` / `MoveAnalysis`：quality、scoreLoss、winRate、bestMove）**早已写完**，是全表"核心已就绪、边际成本最低"的一项。
- **视觉侧本轮无必须 P0 的修复项**：甄塑之原列的头号 P0（令牌作用域收束、红令牌语义拆分）经代码核查确认**已在活动 Web 树交付**，正式作废、不再排期（见 0.1 勘误）。视觉侧仅保留「不做清单」为 P0 设计约束项。
- **范围进一步聚焦**：经玩法 + 技术两票收敛，「多计时档位」与「PGN/FEN 互通」双双降 P2 本轮不做；推演沙盘收敛为桌面单端先验证。

## 3. 玩法设计、棋子设定与平衡性评估（本轮重点）

### 3.1 强度梯度总览（完整模式、全加强基准）

S=过强 / A=强 / B=中 / C=弱 / D=近死子

| 棋子 | 强度 | 独特性 | 结论 |
|---|---|---|---|
| 将/汗 ↑ | **S** | 高 | 过强、胜利条件耦合；需约束而非砍掉 |
| 车 / 炮 | A+ / A | 低 / 中 | 规则锚点，**合理，不建议动** |
| 马 ↑ | **S−** | 中 | 不别腿 + 直走三格可吃，叠加过头，挤压车炮 |
| 相/象 ↑ | A− | 高 | 过河 + 敌境两格，合理偏强 |
| 仕/士 ↑ | C+ | 中 | 慢速机动子，偏弱但合理 |
| 兵/卒 ↑ | **S−/不稳定** | 极高 | 全盘最复杂，最需简化 |
| 尉/卫 | B+ | 中 | 标准主教换皮 + 首着为 0，**刻意平衡合理** |
| 射/䠶（强化/弱化） | B+ / **C** | 极高 | 星轨反直觉、劝退，聪明但过度设计 |
| 檑/礌 | C | 高 | 高机动低攻击，残局子，全期价值不足 |
| 巡/廵 | **D** | 高 | 四重限制叠加，近死子 + 文档矛盾，最该动 |

### 3.3 明确"合理、不建议改"（诚实记录）

- 车、炮作为无开关锚点——规则稳定性基石。
- **`完整 vs 经典只差规则`、`精简 vs 完整只差棋子` 的正交设计非常优雅且合理**，应作为档位体系基座保留。
- 将入敌九宫获胜作为题材标志性胜利条件——叙事契合"匈汉突入"，问题只在强度约束（R1），不在存在本身。
- 尉的标准主教 + 首着为 0——刻意平衡，设计干净。
- 升变"用阵亡子"而非凭空生成——初衷聪明。
- 三连吃子"不吃将"、多格位移不吃子——边界严谨（只是复杂度问题 R5）。
- 刺/甲/楯软删可回滚、精简档去掉尉巡——正确的范围控制。

### 3.4 档位区分度问题

"三套开关"实为两套（`WEB_OPTIONS = COMPLETE_OPTIONS`）；**精简档并未降低规则复杂度**，新手以为"精简=简单"，实则在 22 枚子上玩最复杂的规则。经典档也非纯传统（仍有尉/射/檑/巡与将入敌九宫即胜），需向玩家讲清"经典≠标准象棋"。→ 由 P0-4「轻量规则集预设」从规则侧根治。

> **制作人提示**：R1–R8 中凡触及走法语义者（R1/R2/R3/R4/R5/R6/R8），会因 `RULE_VERSION` 升位 + 三端 7 处触点 + 对拍重跑而成本高，**本轮不直接落地，单独立项走规则变更流程**；R7 文档矛盾与 R9 照面说明属零风险，纳入本轮 P1-13。S4「预登记不再调参」约束的是 **AI 参数**（`core/ai.py::CONFIGS`），与规则语义调整不是同一层面，不冲突。

## 4. 技术可行性与成本（对迭代计划的约束）

— 柯桥良 · 技术架构总监（含勘误 1–3）

**核心判断**：本项目不是"功能少所以难做"，而是"**同源链路多、渲染器多所以改一处贵**"。

- **同源现状**：Python `core/rules.py`（791 行）唯一权威；Web/联机共用 `webapp/js/core/rules.js`，由 bundle 脚本派生；Android 离线是另一份自包含 `offline.js`——**两族镜像、两套守护机制**（83 条对拍守护 Python↔Android，Web 靠 24 MB fixture + 哈希哨兵）。
- **三套渲染器 + 两棵 Web 树**（E-1）：桌面 `board_widget.py` / `web/js/app.js`（426 行，服务端权威规则的轻量客户端）/ `webapp/js/ui/app.js`（2506 行，独立产物树）。两棵 app.js 不同源。凡原"双渲染器翻倍"的成本估算**视为下界**。
- **三个独立版本号**：`RULE_VERSION=3`（走法语义，进 `positionKey`，联机双方须一致）、`FORMAT_VERSION=1`（存档）、`POSITION_KEY_VERSION=4`（重复局面账本）。
- **好做**：陪练档、题库、每日一题、点评展示层——只碰数据层或单侧 UI。
- **贵/高风险**：计时体系、PGN/FEN、推演、大屏横版、主题大批铺开——穿过两族 JS + 三渲染器 + 三版本号，且"两端一致地错"对拍抓不到（历史有 81 条全绿仍分叉的先例，`test_cross_engine.py:229`）。

**架构级风险与规避**：① 触及走法/开局/吃子集合必须**同时对拍两族 JS**、把 offline.js 自建开局路径纳入 fixture、补 perft fingerprint；② fixture 24 MB → 生成出口统一 pop `positionCounts`、设体积门禁；③ 每个状态结构需求先登记"动哪个版本号"并加 CI 一致性断言；④ 渲染改动收敛到共用分发点（如 `_draw_piece`），且**必须先补 `webapp/css` 门禁**（E-2）才谈多主题；⑤ 离线端 movegen 瓶颈（d2 墙钟 53–60%，WASM 不采纳）→ Web/Android 局势评分只做浅层或走服务端 API，**不承诺全端同深度讲解**。

**外部强引擎（Pikafish/NNUE 一类）引擎中立结论**：本轮不接入。唯一可讨论路径是"仅桌面复盘的可选外部 UCI 分析引擎（默认关闭、与对战 AI 完全隔离）"，成本 5–10 人日；作为对战对手与云评测均不建议/不做。重开条件须全满足：`analyze_game(BEGINNER)` 已不够、团队接受额外体积与进程隔离成本、产品确认不需全端一致。

## 5. 棋子平衡优化的落地纪律

平衡建议（R1–R8）价值高但属"规则变更"，与本轮"产品化 + 收敛"主线不同层。**执行纪律**：

1. 凡改走法语义 → `RULE_VERSION` +1，联机版本校验、棋谱旧档兼容、fixture 重生成同步；
2. 走 `core/rules.py` + `offline.js` 双实现同构 + 83 条对拍 + perft 门禁；
3. 强度调整需有样本量支撑（延续项目数据纪律：不凭单局外推），优先用可回滚开关灰度；
4. 与用户裁定"medium↔hard 不再调参、n=64 不做"不冲突（那是 AI 参数，这是规则），但同样不应在本轮顺手做。
