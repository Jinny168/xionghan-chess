# 匈汉象棋 v1.7.0 更新日志

> 本版本主线为「三端规则一致性」与「AI 池感知」，并统一英文术语、重写对外文档。
> 下列条目均可回溯到提交 hash；未落地的事项不列入。

## AI 棋力

- **AI 感知升变池（`f10261f`）**：`_evaluate` 原先只求棋盘之和，导致「吃子」被全额计亏、升变池被当作不存在，单次升变着法被系统性高估约 +900。改为按「盘上 + 池」合并台账补回另一半，权重恒 `1.0`（属补漏，非调参）。池中排除 `KING`（避免 `VALUES[KING]` 爆分），升变项排除 `PAWN`，复活项按 7 兵上限计。
- **池感知缓存键（`f10261f`）**：新增 `evaluation_key` 并**同步**替换置换表 / 评估 / SEE 三处缓存键，避免「同盘面、不同池」串用缓存。
- 规则语义零改动：该提交对 `rules.py` / `game.py` / `offline.js` 各为 0 行改动。
- 现状基线冻结（`dfbb1dc`）：为 AI 池盲立可复跑基线断言。

## 规则内核：`capturable_squares` 统一

- **读侧收敛（`32ff35b`）**：把「谁能吃谁、以何方式吃」从 `in_check` / `_indirect_king_capture` / `_kill_squares` / `_three_cell_neighbours` 等多份实现，收敛为唯一纯函数 `capturable_squares`（`CaptureKind` / `Removal` / `CaptureSpec`）。`in_check` 与离线端 `inCheck` 均派生自它，三端同构；规则语义零改动。
- **写侧收敛（`e470df4`）**：新增 `RulesEngine.board_removals`，成为「一步走法移除哪些子」的唯一写者；`captured_by_move` 是其收窄到敌方的子集；`RESTORE_PAWN_LIMIT = 7` 收敛到唯一出处（原在 `ai.py` 重复一份）。离线端镜像为 `Rules.boardRemovals`。
- **边界固化（`bdeef7b`）**：G11 钉死「甲的三子清线为全盘扫描」这一既有语义——守卫的是**现状**而非期望值，产品若改规则需同步翻转。

## 判和口径：升变池并入 `position_key`

- **口径升级（`403590d`，方案 A，用户拍板）**：capture pool 是游戏状态而非记账——它决定哪些升变合法、能复活多少兵，因此「同盘面、不同池」视为两个不同局面。`position_key` 升为 `<turn>|<board>||pool:<pool>`，新增 `POSITION_KEY_VERSION = 2`；`evaluation_key` 归并为 `position_key` 本身。
- **旧档自动迁移（`403590d`）**：`core/storage.py` 写入 `positionKeyVersion`，读到旧标记（<2）的档时按快照重建判和账本，杜绝读旧档因键口径不同而误判 / 漏判和棋。
- **两端逐字符一致（`b4d9dce`）**：离线端 `positionKey` 排序由字符串序改为元组数值序，与 Python 完全一致。
- **离线档载入重建（`e7ffe02`）**：离线端载入 `.xhgame` 时按快照重建判和账本，与 Python 侧对称。

## 缺陷修复

- **将军假阴性（`742909f`，F2）**：`capturable_squares` 名义池盲实则不然——池非空时「必升变闸门」使裸 move 非法，升变线吃子随之被漏报，`in_check` 假阴性（可能连带将死 / 和棋判定出错）。新增 `promotion_types` / `moves_to_target` 把升变变体构造收成唯一来源；G12 黄金用例钉死「修前 False、修后 True」。其结果仍保持池盲。
- **两端 `position_key` 排序分叉（`b4d9dce`，F1）**：原字符串序把 `"10"` 排在 `"2"` 之前，任何「同色同型、行号跨 1↔2 位」的局面两端账本就此分叉。
- **离线旧档载入漏判和（`e7ffe02`）**：离线端载入时直接 clone 旧账本而不重建，含跨位同型子的旧档第三次回到同一局面时判和永不触发。

## 桌面：棋子图谱与三风格美术（本轮）

- **三风格美术接入**：`web/assets/pieces/{traditional,modern,cartoon}` 的 66 张 160×160 PNG 随包分发（打包进 `xionghan_chess/desktop/resources/pieces`），11 型棋子按 `piece_style` 出图。源图四周有透明留白，运行期按常量裁剪框（传统/卡通 `(12,12,137,137)`、现代 `(7,7,147,147)`）裁到盘径，再按 `dev = 0.78 × cell × DPR` 预缩放、1:1 贴图；盘径与字形模式同一矩形（半径 `0.39 × cell`），切风格不跳大小。
- **默认仍是字形**：新增 `piece_render`（默认 `glyph`），升级后界面**逐像素不变**；「设置 → 外观 → 棋子美术风格」下拉第一项「书法字形（默认）」可随时切回，切回时 `piece_style` 保留原值。
- **棋子图谱**：菜单「帮助 → 棋子图谱」（排在「棋子规则」之上）与设置页「预览三风格」打开同一窗口 —— 左侧 14 子清单（常规 7 + 特色 7，本档案不启用的灰显并注明）、三风格对比条（各有「使用此风格 / 使用中」）、红黑大图 + 名称 + 一句话定位、走法要点（中文取 `PIECE_RULES.md` 对应小节，英文用 `piece_rule.*_long`）、本局规则现状（只读）+ 跳转设置。窗口不依赖对局。
- **即时生效**：「使用此风格」写 `piece_style` + `piece_render="image"` → 重配棋盘 → 重绘；不重建界面、不重开对局，走子数 / 时钟 / 悔棋可用性不变。
- **甲 / 刺 / 楯 暂无三风格美术**，以**同风格棋子底盘 + 随风格字形**呈现：字族随风格（传统＝衬线、现代·卡通＝无衬线）、字重 **Medium**，墨量按判据口径（3 型回退均值 ÷ 11 型位图均值）为 **0.89 / 1.11 / 0.95**（传统 / 现代 / 卡通，落在 0.85–1.25）。三风格仍可区分：**底盘配色与描边粗细不同**；**其余 11 类棋子已接入三风格位图**。未加任何盘外识别标记（`docs/DESIGN_PIECE_MARKERS.md` 仍为下一轮待议）。
- **已知边界（实测，源盘径 traditional/cartoon 137 px、modern 147 px）**：`dev = 0.78 × cell × DPR` 与源盘径之比 —
  - 1920×1080 @200%（cell 70.49）→ dev 110：**0.80× / 0.75×，不软化**；
  - 2560×1440 @200%（cell 97.45）→ dev 165：传统/卡通 **1.20×**、现代 **1.12×**，**5K@200% 起传统/卡通开始轻微上采样**；
  - 3840×2160 @200%（cell 151.39）→ dev 236：1.72× / 1.61×，明显偏软。
  - 未出 2 倍图（会把资产目录推过 512 KB 阈值）；结论：**4K@200% 不软，5K@200% 起传统/卡通略软，现代风到更大尺寸才明显**。
- **性能（62 子单帧，offscreen）**：图片 5.1 ms（840 px）/ 7.7 ms（1470 px），字形 10.6 / 16.5 ms —— 图片模式更快（位图贴图取代字体光栅化）。
## 桌面：AI 与落子的提速

以下三项**没有改动棋力参数**：`CONFIGS`（含 `time_limit` / `randomness`）的增删行数为
**0**（`git diff 55331c1..HEAD -- src/xionghan_chess/core/ai.py` 里筛 `CONFIGS|time_limit|randomness`
无任何增删），跨引擎对拍 **84/84**。

行为侧的口径是分层的，不要读成"选点一定不变"：
- 在 **4 个回归局面**上选点**完全一致**；
- 排序启发式在**同一批局面**下逐项不变（3 档案 × 6 步，分叉 0 次）；
- 搜索深度由 1 提升到 2，**因此未测局面上的选点可能不同**（方向是"同预算看得更深"，不是调参）。

- **落子不再卡顿 230 ms**：`checkmate` / `stalemate` 原来每次都全量枚举合法着法
  （62 枚 × 13×13 目标点，实测 257 ms/次），而 `stalemate` 恰恰在非将军时才执行 ——
  等于**每次落子**都吃这一下。新增 `has_any_legal_move()` 用同一个生成器短路
  （命中即返回），语义与 `bool(legal_moves(...))` 逐局面等价。
  实测 `Game.move`：**中位 2.3 ms**、最大 4.7 ms（仅落子路径；`undo`/新局不走这条链）。
- **着法排序 `_order`：65.1 ms → 30.2 ms**（108 着）。原来给每个着法算「是否将军」
  都要 `apply_unchecked + in_check`（0.5 ms/着）。改为几何预筛：直线兵种看目标格与敌王
  是否共线、近战兵种看步长、移开露子只看源格是否与王共线、甲/刺与升变一律按"可能"处理
  —— **只多算、不漏算**，因此排序逐项不变（3 档案 × 6 步，分叉 0 次）。
- **同预算搜得更深**：`GameState.piece_at` 改为直比 `row/col`（15 万次/5 s）、
  `RulesEngine.enabled_piece_types` 移入构造期预计算（4.6 万次/5 s），并给静态搜索加
  单根着法节点上限 80（含截断计数，被截断的根着法不得成为 best）。
  medium 5 s 同一局面：nodes 59–61 → **109–113**，`completed_depth` **1 → 2**。

- **资产防线**：`web/assets/pieces` 是 Git LFS 跟踪的，构建脚本新增「PNG 魔数 + 160×160 + 单张 ≤24 KB + 目录 300~512 KB + 三风格齐全」断言，未 `git lfs pull` 时构建直接失败（否则会把 66 个指针文件静默打进 EXE）。
