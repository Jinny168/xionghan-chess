## 2. 五条可复用教训

### 2.1 统计上不可认证的目标，不要用「再跑一次」去救

- **现象**：K4 设计带 `[0.65, 0.75]` 只有 10pt 宽，而 n=64 的 Wilson CI 全宽 **19.69pt**。
- **证据**：p≈0.70 时要把全宽压到 10pt 以下需 **n≈320**（约 10 小时机时）；n=64 无论点估计多接近，
  「整个 CI 落在带内」都恒 false。
- **做法**：先算「要多少样本才能认证」，再决定跑不跑；跑的话把目的写成「第二个独立样本 / 稳定性对照」，
  不要写成「认证带内」。结论措辞用「点估计出带、CI 仅与带部分重叠、不可认证」，
  不写「已验证失败」。
- **来源**：游有方（创意总监）裁定；柯桥良（技术架构总监）复算 n 与 CI 宽度。

### 2.2 门禁的判定方向必须与推荐用法一致

- **现象**：`win_rate_pass` 判的是「A 方得分率 ≥0.60」，而脚本 docstring 的推荐用法是
  `--level-a beginner --level-b medium`（A=弱档）——按推荐用法跑，`pass` **必然 false**。
- **证据**：n=64 报告出现 `pass=false` 却 `failedGates=[]`，因为列表漏了 `winRatePass` 这一项。
- **做法**：门禁上线前用「文档推荐的命令」跑一遍，确认它不会必然红；判定层与测量层分离，
  报告带 `judgementVersion`，并新增 `contractPass` 把「脚本门禁」与「设计契约」分开。
  注意 `pass` 是 Python 保留字，局部变量用 `script_pass`。
- **来源**：team-lead 实测定位；柯桥良给出 `strong_low = max(low, 1-high)` 通式与落地 spec。

### 2.3 「进程数 = 2」不等于并发

- **现象**：两个 `python.exe` 命令行完全相同，一度被判为「双进程污染」，据此作废 7 局、停掉 worker。
- **证据**：`.venv/Scripts/python.exe`（274,712 B）是 venv launcher，`sys._base_executable` 指向
  `C:\Python312\python.exe`；实测父进程 `UserMode≈0s`、子进程 `UserMode≈364.9s`，
  `ParentProcessId` 为父子关系，内存 9MB / 46MB 也吻合。
- **做法**：判并发看**父子关系 + CPU 时间 + `sys._base_executable`**，不能只数进程名或比命令行；
  `timeout` / `env` / launcher / base python 是同一条命令的正常四层包装。另外追加写 checkpoint
  （`open("a")` + 每局 flush）时「文件看起来干净（局号连续、无 dup、无坏行）」也不是判据。
- **来源**：team-lead 现场核查与自我纠正。

### 2.4 「不动测量层」必须逐字段列清单

- **现象**：v2 改判定时，曾把 `failedGates` / `pass` 误归入「测量层一律不动」，照字面执行根本无法落地；
  schema 也曾漏数（先说 7 个键，实际 8 个，漏了 `thresholdSide`）。
- **做法**：按「测量层 / 判定层 / 派生层 / 元数据」**逐字段**列表，不用一句口号代替；
  测量层用四组夹具做不变式断言（`[0.5143,0.8205]/137.0/22`、`[0.5789,0.8675]/190.8/22`、
  `[0.3363,0.6637]/0.0/22`、`[0.3424,1.0]/None/None`）。
- **来源**：游有方与柯桥良在 schema 与分层上互相纠错后定稿。

### 2.5 汇报里的数字与归属都必须回查原始回传

- **现象（本轮五次同类错误，全部由 team-lead 犯下）**：
  1. 打包产物报成「100.9 MiB / 11.18 MiB」，实际是 **60.80 MiB（63,756,485 B）/
     29.95 MiB（31,402,472 B）**——数字凭空写，没有核文件；
  2. 把一份并不存在的「27 / 9 / 5」归档分类说成某位成员的回传——同样是凭空写；
  3. 把 #18 的「40 归档 / 13 现行 / 8 组可合并」归到 tech-architect-2 名下——**归属错误**；
  4. 说「历史归档 34 个」——**凭空写**，实际归档 39 个（45 行 − 4 份投稿材料 − 2 份 UI 审计）；
  5. 说索引有「3 条死链」——**说错**：改动前 `broken=0`，只有 `docs/release/RUN.md:38`
     一条**预先存在**的坏链（`[](LINUX_DEPLOY.md)` 应为 `../LINUX_DEPLOY.md`），
     另 3 个只是「未进索引」，不是死链。
- **做法**：数字先跑命令；引用 teammate 的结论时，回查**原始回传原文**，写清是谁在哪一条里说的。
  归属与数字一样是事实，不能凭印象；转述时必须贴原文块（这条 2026-11-09 已立过规矩，本轮又犯）。
- **代价**：第 3 条会让后来者按错误归属追溯、找不到真正作者——这是**可审计性问题**，不是礼貌问题。
- **防错机制（由 tech-architect-2 提出，已采纳）**：
  1. **引用三重锚点**：跨人引用的数字 / 清单必须同时带 ① 来源人 ② task id ③ 原句摘录或
     `文件:行号`；三者缺一，写成「待核」，不写精确值。
  2. **数字同段可回溯**：复盘里每个数字，同段内必须能追到原始回传原句；追不到就写「约 / 待核」，
     不写小数位——「100.9 / 11.18 MiB」这类最危险，因为它看起来太精确，反而没人去核。
  3. **归属一律用 task id，不用人名**：本队同时存在 `tech-architect` 与 `tech-architect-2`，
     写人名极易串；写「#18 产出」。
  4. **retro 附引用清单表**（见 §6）：`数字 | 来源 | task id | 原句或文件 | 已回查`。
     这张表本身就是审计证据，下一轮复盘可直接复用。
- **来源**：team-lead 自省；第 3 条由 tech-architect-2 只读复核指出；四条机制由 tech-architect-2 提出。
- **本轮新增两条教训**：
  - **引用配置字段前先确认它是不是 `dynamic`**：`pyproject.toml` 的 `version` 是
    `dynamic = {attr = "xionghan_chess.__version__"}`，没有静态值可比；
    唯一的版本源是 `src/xionghan_chess/__init__.py` 的 `__version__`（= 2.0.0）。
  - **结构性坑要单独查，不能靠「看起来正常」**：`.gitignore` 里的裸 `archive/`、`release/`
    会匹配**任意层级**，导致 `docs/archive/` 以后静默吞文件（本轮已有文件被 `git add -f`
    强行入库才没丢）；应写成 `/archive/`、`/release/`（只匹配仓库根层级）。

## 3. 下次标定照做（清单）

1. **先算样本量**：目标带宽度 W → 要 CI 全宽 < W 需要多少 n；算不出来就别承诺「认证」。
2. **预登记判读规则**写在跑之前，含「至多一次调整、不循环、不扩 n」，并写明不执行时的原因性质
   （统计判断 / 运行条件）。
3. **单进程、恒定 `--n`、`--resume` 分批**；启动前后用进程树确认无残留；长跑不要与全量测试并发。
4. **每次汇总用独立复算**（`_verify_n64_recompute.py`）核对 20 组字段，不调用 `summarize` 自证。
5. **测量层 / 判定层 / 契约层分离**；报告带 `judgementVersion`、`contractPass`、`contractFailedGates`。
6. **结论写法**：观测值 + CI + 是否可认证 + 未达标项，逐条列；不把 `pass=true` 当验收通过。
