# 2026-10-24 · 网页版重构与 1024 大赛投稿

## 目标

把匈汉象棋投稿到 WorkBuddy「1024 造物挑战」。比赛要求「网页应用 + 公网可体验链接」，
而原 `web/` 只是 FastAPI 的前端壳子，无法静态部署。

## 关键决策

1. **把规则内核移植到 JavaScript**，而不是部署 Python 服务。
   理由：评审点开链接要立刻能玩；静态托管没有冷启动、没有 WebSocket、没有运维。
   代价：约 1,900 行移植 + 必须证明规则一致。
2. **单文件构建**。WorkBuddy「发布为网站」的分享链接首访只授权 HTML 文档，
   子资源（CSS / 多个 JS 模块）会 403，刷新后才正常。把 CSS、模块、AI Worker
   全部内联进一个 HTML（267 KB）后，首访即可玩。
   构建脚本：`scripts/build_webapp_bundle.py`（自研 ES 模块打包，无外部依赖）。

## 产出

- `webapp/js/core/` —— model / profiles / rules / game / movegen / ai，逐行对应 Python `core/`
- `webapp/js/ui/` —— Canvas 棋盘、WebAudio 音效、主控
- `webapp/tests/` —— 两道规则门禁
- `webapp/dist/index.html` —— 发布产物
- `docs/WEBAPP_1024.md` —— 投稿 13 项字段的现成文案
- `scripts/gen_rule_fixtures.py` —— Python 侧黄金用例生成器

## 踩过的坑

- **隔子跳跃棋子（尉/卫、楯/碷）可以跳过任意距离**，不是固定两格；快速生成器最初写成两格，
  被门禁抓出。
- **仕/士出宫后可直走**，候选生成必须包含四正方向。
- **`applyUnchecked` 中途会 splice 棋子**，惰性棋盘索引 `_grid` 必须在使用后 `delete`，
  否则搜索结果读到过期棋子。
- **首帧在布局完成前绘制**，`createLinearGradient` 收到非有限值会抛错；渲染器需守卫。
- **9×10 棋盘不能用正方形画布**，必须按行列比推高度。
- **AI Worker 的相对路径**写成了 `../core/`（应为 `./core/`），一直静默回退到主线程。

## 模型入浏览器：评估后放弃（12:48—13:00）

- 权重 `training-data/policy-value-v1.npz` 4.19 MB：w1 4901×32、wp 32×28561（策略头 3.5 MB）、
  wv 32×1。输入 29×13×13，输出 28561 个 from-to。
- 放弃理由：① 单文件从 324 KB 涨到 5 MB 量级（即使 int8 量化也要 1.2 MB）；
  ② 1.6.0 自述「50 局胜率 ≥55% 未完成验收」，棋力未证；③ 编码/动作索引必须与训练完全对齐，风险高。
- 改为强化搜索：negamax 加 LMR（depth≥3、第 4 手起安静着法减 1 层，第 8 手起减 2 层，
  fail-high 再补搜）。节点 -7%，未出现非法着法。
- 结论：13 路分支因子 ~100，depth 4 需 3–5M 节点 ≈ 30 s，4.2 s 内到不了。
  master 维持 depth 3 + 静态搜索 8 层，不宣称 MCTS 级棋力。
- 360px 移动端检查：14 个登场棋子、5 档难度、7 个工具条按钮均可读，无横向溢出。
- 线上最终验收：5 档 / 6 个侧栏动作 / 走子与应手正常 / 0 报错；单文件 324.4 KB。
